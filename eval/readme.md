# Ctrl-World Evaluation Framework

## 1. Overview

This directory contains a modular evaluation framework for assessing the quality of videos generated by the Ctrl-World world model.

The framework evaluates generated future observations against their corresponding ground-truth observations using pixel-level, structural, perceptual, temporal, motion-based, and video-distribution metrics.

The evaluation operates on previously generated rollout data. It does not initialize or execute the Ctrl-World model, generate new rollouts, or evaluate robot-policy performance.

### Objectives

The evaluation framework aims to measure:

- Pixel-level visual fidelity between predicted and ground-truth frames.
- Structural and perceptual similarity.
- Temporal consistency across consecutive frames.
- Motion prediction quality.
- Video realism at the distribution level.
- Prediction quality across different camera views.
- Degradation in prediction quality over increasing prediction horizons.

## 3. Input Data

The evaluation framework uses the paired prediction and ground-truth NPZ files generated by the existing Ctrl-World rollout pipeline.

The existing rollout generation code saves evaluation data under a structure similar to:

```text
synthetic_traj/
└── <task_name>/
    └── evaluation_data/
        └── trajectory_<DROID_ID>/
            ├── interaction_0_start_<frame>.npz
            ├── interaction_1_start_<frame>.npz
            └── ...
```

The NPZ files contain fields including:

- `ground_truth`: Ground-truth video observations.
- `prediction`: World-model predicted observations.
- `trajectory_id`: Trajectory identifier.
- `interaction_index`: Interaction segment identifier.
- `start_frame_index`: Starting frame of the interaction.
- `instruction`: Associated instruction.
- `fps`: Video frame rate.
- `frame_indices`: Corresponding frame indices.

The actual array dimensions, camera ordering, image format, and data ranges must be verified against the existing rollout implementation before evaluation.

The loader must preserve the correspondence between predicted and ground-truth observations.

### Input requirements

- Prediction and ground-truth frames must be aligned.
- Both videos must have compatible dimensions.
- Camera views must be identified correctly.
- Invalid or incomplete samples must be reported.
- Shape mismatches must not be silently corrected.
- Original input files must remain unchanged.

## 4. Evaluation Metrics

The framework implements the following complete metric suite.

### 4.1 Pixel-Level Visual Fidelity

These metrics measure the numerical difference between predicted and ground-truth images.

| Metric | Description | Better result |
|---|---|---|
| MSE | Mean Squared Error between corresponding pixels | Lower |
| PSNR | Peak Signal-to-Noise Ratio, measuring reconstruction quality | Higher |

These metrics provide a baseline measurement of pixel-level prediction accuracy.

### 4.2 Structural and Perceptual Similarity

These metrics evaluate visual similarity beyond direct pixel differences.

| Metric | Description | Better result |
|---|---|---|
| SSIM | Structural Similarity Index, measuring luminance, contrast, and structural similarity | Higher |
| LPIPS | Learned Perceptual Image Patch Similarity, measuring deep-feature perceptual differences | Lower |

LPIPS uses a pretrained feature network. The implementation must handle model weights and optional dependencies explicitly without silently downloading weights.

### 4.3 Temporal Consistency

Temporal metrics evaluate whether the generated video preserves changes across consecutive frames.

**Temporal Difference Error**

Compares frame-to-frame changes in the predicted video with corresponding changes in the ground-truth video.

This helps identify:
- Unnatural frame-to-frame changes.
- Missing or exaggerated motion.
- Temporal instability.
- Differences in object movement over time.

The metric must compare consecutive-frame changes rather than treating each frame independently.

### 4.4 Optical-Flow-Based Motion Comparison

Optical flow estimates apparent motion between consecutive frames.

The evaluation compares motion estimated from:
- Predicted video frames.
- Ground-truth video frames.

It measures differences in estimated motion patterns and provides a diagnostic of motion prediction quality.

Important distinction: Estimated optical-flow differences are not ground-truth optical-flow endpoint error unless annotated ground-truth flow is available.

The implementation must clearly identify which type of comparison is being reported.

### 4.5 Video Distribution and Realism

**Fréchet Video Distance (FVD)**

FVD measures differences between distributions of real and generated video clips using video feature representations.

It complements individual reference-based metrics by evaluating video-level distributional similarity.

Requirements:
- Calculate FVD over collections of video clips, not individual frames.
- Use a suitable pretrained video feature extractor.
- Make the feature extractor configurable.
- Handle clip length and preprocessing consistently.
- Report insufficient sample counts or incompatible inputs.
- Do not silently download pretrained weights.

FVD is a dataset-level metric and should not be interpreted as a per-frame reconstruction score.

### 4.6 Multi-Camera Evaluation

The framework evaluates each available camera independently.

For each camera, calculate the applicable metrics:

- MSE.
- PSNR.
- SSIM.
- LPIPS.
- Temporal Difference Error.
- Optical-Flow-Based Motion Difference.

The results should preserve camera identifiers and allow comparison between camera views.

Raw pixel comparisons between different camera views must not be performed unless valid geometric correspondence is established.

---

## 5. Prediction-Horizon Analysis

Prediction quality must also be analyzed across the future prediction horizon.

For every applicable metric, report how the value changes as the predicted frame moves further into the future.

This analysis helps identify:

- Whether visual fidelity degrades over time.
- Whether structural details are progressively lost.
- Whether motion predictions become less accurate.
- Whether temporal instability increases at longer horizons.
- Whether degradation differs across camera views.

Prediction-horizon plots should use actual frame indices or elapsed prediction time, based on the available metadata.

---

## 6. Aggregation and Reporting

Metrics must be reported at multiple levels.

| Level | Description |
|---|---|
| Frame-level | Metric values for individual predicted frames |
| Interaction-level | Aggregated metrics for each interaction segment |
| Trajectory-level | Aggregated metrics for each trajectory |
| Camera-level | Metrics reported independently for each camera |
| Horizon-level | Metrics grouped by prediction horizon |
| Dataset-level | Overall evaluation across valid samples |

For applicable metrics, report:

- Mean.
- Median.
- Standard deviation.
- Valid sample count.

Aggregation must preserve the relationship between trajectories, interactions, cameras, and frames.

Overlapping interaction boundaries must be handled carefully to prevent accidental double-counting when calculating trajectory-level or dataset-level results.

FVD must be reported at the appropriate video-collection level rather than incorrectly assigning it to individual frames.

The framework generates qualitative and quantitative visualizations.

### Quantitative plots

- Metric distributions.

- Per-camera metric comparison.

### Qualitative comparisons

## 8. Module Responsibilities

### `data_loader.py`

- Discover evaluation NPZ files.
- Load predictions, ground truth, and metadata.
- Preserve trajectory, interaction, camera, and frame information.
- Check data compatibility.
- Provide a consistent data structure to metric modules.

### `validate_data.py`

- Validate required NPZ fields.
- Check array dimensions and data types.
- Verify prediction and ground-truth compatibility.
- Check frame counts and image dimensions.
- Validate camera information and metadata.
- Report invalid samples and warnings.

### `metrics/pixel_metrics.py`

Implements:
- MSE.
- PSNR.

### `metrics/perceptual_metrics.py`

Implements:
- SSIM.
- LPIPS.
- FVD.

FVD is computed across video collections using an appropriate pretrained video feature extractor. It must not be treated as an individual frame metric.

### `metrics/temporal_metrics.py`

Implements:
- Temporal Difference Error.
- Optical-Flow-Based Motion Difference.

The implementation must clearly distinguish estimated flow differences from true endpoint error against annotated ground-truth flow.

### `metrics/multiview_metrics.py`

- Compute metrics independently for each camera.
- Preserve camera identifiers.
- Generate camera-wise comparisons.
- Support multi-camera result aggregation.

### `aggregation.py`

- Frame-level aggregation.
- Interaction-level aggregation.
- Trajectory-level aggregation.
- Camera-level aggregation.
- Prediction-horizon aggregation.
- Overall dataset-level aggregation.

### `visualization.py`

- Generate metric plots.
- Generate frame comparisons.
- Generate side-by-side videos.
- Save visualizations to the current evaluation run directory.

### `utils.py`

Contains shared functionality:
- Configuration handling.
- Logging.
- Directory creation.
- File naming.
- JSON serialization.
- Common utility functions.

### `run_evaluation.py`

The main entry point coordinating the complete evaluation process.

It:
1. Parses command-line arguments.
2. Loads the evaluation configuration.
3. Discovers saved rollout files.
4. Validates input data.
5. Calculates selected metrics.
6. Aggregates results.
7. Saves CSV and JSON reports.
8. Generates plots and visual comparisons.
9. Prints an evaluation summary.

It must never execute the Ctrl-World model or generate new rollouts.

## 9. Running Evaluation

Evaluation should operate directly on existing generated NPZ files.

Example command structure:

```bash
python -m eval.scripts.run_evaluation \
    --input_dir synthetic_traj/<task_name>/evaluation_data \
    --output_dir eval/results \
    --metrics all \
    --device cuda \
    --save_visualizations
```

The exact command and supported arguments must match the implemented CLI.

Supported configuration should include:

| Argument | Purpose |
|---|---|
| `--input_dir` | Directory containing evaluation NPZ files |
| `--output_dir` | Directory for evaluation results |
| `--metrics` | Selected metrics or all metrics |
| `--device` | CPU or CUDA where supported |
| `--batch_size` | Batch size for applicable metric computations |
| `--save_visualizations` | Enable or disable visual outputs |

Optional metrics must provide informative dependency errors when their required packages or pretrained weights are unavailable.

A failure in one optional metric should not unnecessarily prevent the other metrics from running.

## 12. Interpretation and Limitations

Reference-based metrics compare generated predictions against one recorded future observation.

However, a world model may produce a physically plausible future that differs visually from the particular recorded future.

Therefore:
- Pixel metrics should not be interpreted as a complete measure of physical correctness.
- SSIM and LPIPS provide complementary visual similarity measurements.
- Temporal and optical-flow metrics help diagnose motion-related errors.
- FVD measures distribution-level video similarity, not exact trajectory correctness.
- Multi-camera scores should be interpreted independently unless geometric correspondence is available.

Metric results should be interpreted together with qualitative video comparisons.

The framework measures generated video quality; it does not measure robot-policy success or task completion.

## 13. Reproducibility

For every evaluation run, record:

- Input directory.
- Evaluation timestamp.
- Metric configuration.
- Device used.
- Batch size.
- Preprocessing settings.
- Dependency and feature-extractor configuration.
- Number of valid and invalid samples.
- Metric-specific sample counts.

This information should be saved in `config.json` and `summary.json` wherever applicable.

The same input data and configuration should produce reproducible evaluation results, subject to numerical differences across hardware and library implementations.
